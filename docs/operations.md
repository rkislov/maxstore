# Эксплуатация

## HTTPS

По умолчанию оба порта доступны только на localhost. Для внешнего доступа поставьте reverse proxy с HTTPS, задайте `S3_PUBLIC_ENDPOINT` и `COOKIE_SECURE=true`. Сохраните исходный Host и URI запроса S3: их изменение ломает SigV4. Не добавляйте префикс к S3 endpoint и не нормализуйте ключи со слешами. Для больших файлов отключите буферизацию тела и задайте достаточные тайм-ауты и лимиты тела proxy.

Пример Caddy для двух доменов (замените домены):

```caddyfile
console.example.com {
    reverse_proxy 127.0.0.1:8080
}
s3.example.com {
    reverse_proxy 127.0.0.1:9000
}
```

При прямом запуске Go TLS завершается на proxy. Облачные мессенджеры вызываются по HTTPS с проверкой сертификата.

## Резервная копия

1. Остановите MaxStore штатно (SIGTERM; для Docker `docker compose stop`).
2. Скопируйте **весь DATA_DIR**, включая `metadata.db`, `master.key`, `credentials.json`, локальные `chunks` и все остальные файлы. Не копируйте активно изменяемую БД обычным `cp`.
3. Сохраните отдельно необходимые настройки провайдеров и секреты окружения.
4. Запустите сервер и проверьте `/healthz`, вход и скачивание контрольного файла.

Для Docker именованный том можно архивировать отдельным контейнером после остановки сервиса. Копия метаданных не содержит Telegram/MAX-части: для независимой резервной копии скачайте объекты в другое хранилище через S3. Сам архив DATA_DIR тоже содержит ключи и должен храниться закрыто.

Восстановление: остановите сервер, восстановите каталог целиком, верните владельца/права, подключите прежнего бота с доступом к прежнему чату и запустите одну реплику. Проверьте контрольные суммы нескольких объектов. Не создавайте новый master.key поверх существующих данных.

## Обновление

Сначала резервная копия и остановка, затем новый бинарный файл или `docker compose up -d --build`. Изменения схемы метаданных в этой версии добавляют необязательные JSON-поля и сохраняют чтение старых объектов. Откат проверяйте на копии данных. Доступные в предыдущей версии функции могут отсутствовать в старом бинарнике.

## Диагностика

- 401 в консоли: проверьте логин, пароль и срок сессии; при Secure cookie используйте HTTPS.
- 403 SignatureDoesNotMatch: Host, path-style, регион, время, ключи и преобразования URI на proxy.
- 429 провайдера: уменьшите число потоков; интервал отправки и retry_after сохраняются независимо от выбора в браузере.
- 501 от S3: операция или формат streaming payload не входят в поддерживаемый профиль; [настройки клиентов](s3.md).
- После обновления страницы: выберите исходный файл снова, части восстановятся из серверной сессии.
- Растёт очередь очистки: провайдер запрещает удаление либо временно недоступен. Telegram может не удалить старые сообщения.
- `configured`/«Настроен» не означает доступность удалённого API.

Структурированные логи пишутся в stderr. Не публикуйте логи провайдеров без проверки: сетевые ошибки могут содержать URL с токеном. Данные и диагностические артефакты исключены из git и Docker build context.
